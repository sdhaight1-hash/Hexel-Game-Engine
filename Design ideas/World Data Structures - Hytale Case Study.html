1. Executive summary

Hytale's official server API documents a world chunk containing a BlockChunk, and a separate BlockSection component that exposes palette-backed block access, filler and rotation values, lighting data, changed-position access, and ticking-block operations. The palette API documents several representations: EmptySectionPalette, HalfByteSectionPalette, ByteSectionPalette, and ShortSectionPalette. This is strong evidence that Hytale's public API models section block storage using multiple palette forms; it does not by itself establish every runtime selection rule or the exact memory cost of a particular section.

Hytale's world-generation guide describes density fields as coordinate-based decimal values used to define terrain shape. Positive values are typically interpreted as solid and negative values as empty space, and material-provider nodes choose block assets for terrain regions. This is a generation model, not a claim that the runtime world stores a live density value for every block.

Recommendation for Hexel: keep the authoritative terrain representation independent from generation functions and derived systems. Evaluate section-local palettes as a candidate for dense regions, but compare them against Hexel's sparse occupied-cell baseline. Model density or field-based generation as a way to produce cell occupancy/materials, not as a replacement for saved edits.

Evidence rule: documented API facts are distinguished from design interpretations. JSON below is illustrative Hexel data modeling, not Hytale's internal chunk file format or a claim about its actual serialized schema.

3. Chunk and section hierarchy

The WorldChunk API describes a world chunk as a component containing a BlockChunk and tracking whether it should be unloaded. The BlockChunk API identifies a chunk coordinate pair via its X and Z accessors, exposes saving-state methods, and references a HeightmapColumn. The section package documents ChunkSection as a component representing one chunk section, with section coordinates, a reference to the owning chunk column, and keep-alive/active timers that drive section-level unloading.

The documented model therefore distinguishes a chunk-column-level object from vertically located sections. The section API is the more relevant unit when investigating local block storage and updates. This differs from treating the entire world as one global flat collection.

World / chunk store | +-- WorldChunk component (lifetime / chunk flags) | +-- BlockChunk component (column-level data and save state) | +-- ChunkSection components at section coordinates | +-- BlockSection (block palette + auxiliary values) +-- FluidSection (separate fluid-related component) +-- EnvironmentSection (vertical runs per column) +-- EntitySection / block-component sections (other data)

This diagram is a conceptual synthesis of documented class/package relationships, not a complete UML diagram or a claim that every component is always present. The section package explicitly lists separate block, fluid, environment, entity, lighting, and block-component-related types.

Useful section-level operations

BlockSection exposes get(index) and get(x,y,z), corresponding setters, count(), count(id), contains(id), and find(...) methods for locating requested block IDs. It also exposes getAndClearChangedPositions(), cached chunk-packet methods, serialization/deserialization methods, and ticking-block operations. These are signs of an API built around local section operations rather than requiring all callers to scan an entire world.

The API documents the index overload and the coordinate overload, but this study does not assume a specific index formula unless verified in the linked coordinate utility documentation. For Hexel, we must define and test our own axial (q,r,y) mapping.

4. Palette variants and indexed cells

The official palette package lists four implementations under AbstractSectionPalette: EmptySectionPalette, HalfByteSectionPalette, ByteSectionPalette, and ShortSectionPalette. The abstract API documents operations including get(index), set(index,id), contains(id), count(id), find(ids,...), values(), valueCounts(), promote(), demote(), and shouldDemote().

The existence of promotion/demotion methods and multiple palette types suggests the representation can vary according to the stored values or storage needs. That is a reasonable inference from the API surface, but exact thresholds, bit layout, selection policy, and memory footprint should not be asserted without inspecting the concrete class contracts or measuring the implementation.

The BlockSection constructor accepts separate palettes for its chunk block values, filler values, and rotation values. This documents a separation of these value categories. It does not mean the values should be duplicated into one full object per cell in Hexel.

Conceptual example

palette = [air, stone, soil, water]
cell indices = [0, 1, 1, 2, 0, 3]

This illustrates palette-indexed cells: palette entries map compact per-cell indices to semantic material IDs. It is not Hytale's actual encoding and is not evidence that every palette implementation uses this exact arrangement.

5. Auxiliary data, lighting, changed positions, and saving

The BlockSection API documents separate getter/setter paths for local and global light data, methods to invalidate each light layer, change counters, a sky-lit stamp, filler values, rotation values, and a loaded flag. The documentation says loaded controls whether changes are tracked for replication; changes made before the chunk is loaded can be ignored because the full chunk will be sent anyway.

The same class exposes getAndClearChangedPositions(), a set operation accepting block ID, rotation, and filler, plus methods to serialize for packets or general serialization. These provide documented hooks for distinguishing changed block locations, light invalidation, and network replication state.

The BlockChunk API separately documents markNeedsSaving(), getNeedsSaving(), and consumeNeedsSaving(). It also documents invalidateColumnPacket(), which drops a cached column packet for rebuilding and must be called when column heightmap data changes, otherwise clients may receive stale heightmap information.

These are distinct responsibilities: persisted-state dirtiness, changed cell positions, lighting invalidation, and cached-packet invalidation. Avoid collapsing them into a single generic dirty flag in Hexel.

Separate component types

  • Block values: core cell material/state.
  • Filler and rotation: separately accessed values associated with a block location.
  • Lighting: local/global light data with explicit invalidation APIs.
  • Fluids: a separate FluidSection appears in the official section package; the BlockSection version notes also say fluids are no longer blocks.
  • Environment: EnvironmentSection stores environment data as vertical runs per column, and its builder consumes runs from bottom to top.
  • Block-associated components: BlockComponentSection documents per-section storage keyed by a section-local block index.
  • Save/replication/cache state: saving flags, changed positions, loaded state, and packet invalidation are exposed separately.

This separation is relevant to Hexel's planned terrain fields and reactive invalidation system: only systems affected by a change should be scheduled, and derived caches should have explicit invalidation rules.

6. Density-field terrain generation

Hytale's official Density Generation Concepts guide says terrain shape is founded on density fields—maps of decimal values built from procedural noise such as Simplex and Cellular, contextual data, and processing nodes. It describes values typically ranging from 1 to -1, with positive values usually representing solid terrain and negative values representing empty space. The guide also describes combining heights with a noise field to produce 3D terrain.

The official Materials Generation Concepts guide describes material-provider nodes that select block assets at locations. It describes splitting positive density values into a solid provider and negative values into an empty provider, and priority queues for material selection. Providers may also run on negative portions to place content such as water levels.

Generation is not the same as runtime storage

A density field can be thought of as a function that classifies locations based on a scalar value. It can generate cave-like voids and complex shapes when the field varies in three dimensions. However, the documentation does not establish that the runtime stores density floats for every cell after generation. A likely conceptual pipeline is: evaluate generation fields, decide solid/empty and material, then write results into the runtime world representation.

Noise + contextual fields + curves | v Density evaluation | +-------+-------+ | | positive value negative value | | solid/material empty or fluid/material rules | v generated cell state | v runtime section storage

This pipeline is a conceptual interpretation of the documented generator concepts, not a statement of Hytale's exact internal execution order.

Implications for Hexel

Density-based generation could complement Hexel's axial-prism world. A 3D scalar field evaluated at cell centers could determine whether a hexel exists, while a separate material function chooses its material. This is especially promising for caves, tunnels, arches, and overhangs that a heightmap-only generator cannot represent. Hexel would still need explicit coordinate sampling rules, stable seed behavior, boundary handling, and a way to preserve player edits when regenerating or loading cells.

7. JSON examples for Hexel

The examples below are illustrative Hexel schemas, not Hytale file formats. The official Hytale docs state that the asset reference describes JSON formats for assets loaded by the server, and that content definitions can be edited as assets. That does not mean world chunk cell data itself is stored in these JSON structures.

Example A — a section with a palette

{
  "section": {
    "coord": { "q": 2, "r": -1, "y": 0 },
    "dimensions": [16, 16, 16],
    "storage": "palette",
    "palette": ["air", "stone", "soil", "water"],
    "cell_indices_example": [0, 1, 1, 2, 0, 3],
    "version": 1
  }
}

The cell array is abbreviated and only illustrates the mapping from cell index to palette entry. A production format must define exact ordering, encoding, palette transitions, versioning, and behavior when material IDs change.

Example B — sparse occupied-cell storage

{
  "section": {
    "coord": { "q": 2, "r": -1, "y": 0 },
    "storage": "sparse",
    "occupied_cells": [
      { "local": [0, 0, 0], "material": "stone" },
      { "local": [1, 0, 0], "material": "stone" },
      { "local": [1, 1, 0], "material": "soil" },
      { "local": [8, 4, 12], "material": "stone" }
    ]
  }
}

This is readable and represents only occupied cells. It may be attractive for very sparse sections, but a JSON object per cell has substantial overhead for high-volume runtime storage. A Rust implementation could use a sparse map/set or a packed representation instead.

Example C — generation configuration, not stored cell data

{
  "terrain_generation": {
    "seed": 987654321,
    "density": {
      "type": "combined_field",
      "height_field": "continental_height",
      "noise_field": "cave_noise",
      "solid_when": "density > 0"
    },
    "materials": [
      { "when": "near_surface", "material": "grass" },
      { "when": "density > 0", "material": "stone" },
      { "when": "density <= 0", "material": "air" }
    ]
  }
}

This is a conceptual sketch, not valid Hytale generator JSON and not a complete procedural-generation schema. It shows the distinction between rules that generate terrain and the cell state that results from those rules.

Example D — independent invalidation domains

{
  "runtime_section_state": {
    "coord": { "q": 2, "r": -1, "y": 0 },
    "persistence_dirty": true,
    "changed_cells": [[3, 4, 5]],
    "mesh_dirty": true,
    "lighting_dirty": false,
    "surface_summary_dirty": true
  }
}

All fields here are proposed Hexel runtime concepts, not Hytale API field names. They illustrate that one edit can require a save and mesh update without necessarily invalidating lighting.

Example E — column occupancy summary

{
  "column_summary": {
    "local_q": 4,
    "local_r": 7,
    "occupancy_y_bits_low": "00000000000000000000000000000001",
    "occupancy_y_bits_high": "00000000000000000000000000000100"
  }
}

This sketch is inspired by the documented columnOccupancy API, which produces two 32-bit occupancy masks per column and encodes classification bits over section-local Y positions. The sample bit strings are purely illustrative; they do not describe an actual Hytale column or Hexel's final bit layout.

8. Architecture implications for Hexel Engine

Authoritative axial-prism cells (q, r, y) | edits / generation / load | v Change tracking layer / | | \ v v v v Mesh Lighting Surface Persistence cache system summary / save ^ | Density/material generator (produces initial cell state)

Recommended conceptual responsibilities:

  • Authoritative cell state: independent 3D occupancy and material state, including empty cells, tunnels, and overhangs.
  • Section-local storage: compare sparse, dense, and palette-indexed candidates; do not assume Hytale's implementation is optimal for Hexel's hexagonal coordinate geometry.
  • Material/state separation: consider whether rotation, shape variants, fluids, or other per-cell properties should be stored independently from base material IDs.
  • Derived occupancy masks: test small bitset summaries for surface queries and neighbor/visibility acceleration, while retaining full cell state.
  • Lighting and mesh invalidation: separate flags and update queues; track neighboring chunk effects for exposed faces.
  • Generation fields: allow procedural density/material functions to initialize terrain, but ensure player edits and persisted state are authoritative after generation.
  • Persistence and streaming: define section lifetime, save dirtiness, and unload/reload rules separately from mesh cache lifetime.

For Hexel's pub/sub or dependency system, use notifications to identify affected systems and regions, batch changes, deduplicate work, and query authoritative state when recomputing. Do not make every cell subscribe to every field or rebuild every derived product after every edit.

10. Recommended experiments

  1. Preserve the baseline. Benchmark Hexel's current sparse occupied-cell structure before changing it.
  2. Generate controlled fixtures. Include empty sections, solid terrain, mixed materials, cave systems, tunnels, overhangs, and high-diversity structures.
  3. Compare storage candidates. Sparse cells, dense indexed cells, fixed-width palette indices, and adaptive palette variants should share the same fixtures and workload.
  4. Measure palette transitions. Repeatedly add/remove material types in a section and record conversion cost, memory and correctness.
  5. Test auxiliary summaries. Compare full scans with occupancy bit masks for surface detection, exposed-face meshing, and local queries.
  6. Prototype density generation separately. Evaluate a deterministic scalar field over Hexel cell centers, map its sign to occupancy, and select material with a separate function. Test seeds, negative axial coordinates, caves and chunk-boundary continuity.
  7. Keep dirty domains independent. Measure persistence, mesh rebuild, lighting and summary work separately after edits, including edits across chunk boundaries.
  8. Test round trips. Verify coordinate/index mapping, serialization versioning, empty-section handling, palette promotion/demotion, and unload/reload behavior.
  9. Decide from results. Adopt adaptive palettes only if measured gains justify the additional implementation complexity.
