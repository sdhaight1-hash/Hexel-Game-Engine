1. Executive summary

Vintage Story’s public API describes a chunk system that is more structured than one undifferentiated block array. The documented interfaces distinguish block data, lighting, light-source indices, block entities, entities, and two-dimensional map data. Its IChunkBlocks interface exposes indexed block access and palette-aware operations.

The most transferable design lesson for Hexel Engine is separation of authoritative 3D cell state from derived or auxiliary data. Hexel should retain independent occupancy for each axial coordinate and vertical layer so that caves, tunnels, arches, overhangs, and floating structures are representable. Surface-height or regional summaries can accelerate selected queries, but must not replace the authoritative 3D data.

Recommendation: do not choose dense storage, sparse storage, or palette encoding solely because Vintage Story exposes palette-related APIs. Benchmark Hexel’s current sparse representation against dense indexed chunks and a palette-indexed candidate using representative terrain, edit patterns, and mesh workloads.

Evidence rule: this study separates facts explicitly documented by Vintage Story’s public API from interpretations and proposed Hexel designs. The JSON structures below are illustrative Hexel schemas, not Vintage Story’s actual serialized format.

2. Sources and evidence boundaries

  • Vintage Story API repository — user-selected reference repository.
  • IChunkBlocks API documentation — block access and palette-related operations.
  • IWorldChunk API documentation — 3D chunk interface and associated data.
  • IMapChunk API documentation — 2D map data for one chunk column.
  • IBlockAccessor API documentation — block access and mutation operations.

What the evidence does and does not prove

The API docs explicitly document a linear 3D index formula for block and lighting access, and palette-aware behavior in IChunkBlocks. An interface contract does not, by itself, prove the complete concrete memory layout, bit-packing scheme, compression ratio, allocation strategy, or the exact bytes used per chunk. Those details need confirmation from accessible implementation code or measurements.

The public repository is an API reference, not a license to assume every implementation detail is exposed. Review the repository’s license before reusing code. This document describes design concepts and does not copy implementation code.

3. 3D chunk data and indexing

The IWorldChunk.Data documentation says it holds block IDs for each coordinate and documents this linear index formula:

index = (y * chunksize + z) * chunksize + x

For chunk size S and local coordinates (x, y, z), this maps the three coordinates to one integer index. For an illustrative 32 × 32 × 32 chunk, local position (3, 5, 7) maps to:

index = (5 * 32 + 7) * 32 + 3
      = 5347

Why linear indexing is useful

  • Direct access: coordinates can be converted to an index with arithmetic rather than a hash lookup.
  • Predictable traversal: sequential index iteration is convenient for whole-chunk processing.
  • Compact addressing: the cell’s coordinate need not be stored alongside every indexed value.
  • Dense-grid cost: a slot exists for every possible cell, including empty cells, unless another representation compresses or omits them.

The 32-cell example is explanatory, not a recommendation for Hexel. The IChunkBlocks documentation also describes a bulk-setting operation with a special constraint involving lenX being treated as 32. Do not infer that every API operation accepts arbitrary dimensions.

Adapting the concept to Hexel

Vintage Story’s formula is for rectangular local coordinates (x, y, z). Hexel’s horizontal coordinates are axial (q, r), plus vertical layer y. We can still use a linear local index once chunk-local coordinates have been normalized, but we must define the mapping for the chosen hexagonal-prism chunk layout and test negative world coordinates, chunk boundaries, and round-trip conversions.

4. Palette-related operations

The IChunkBlocks documentation exposes a palette-aware interface. Relevant documented operations include:

API featureDocumented behaviorPotential design lesson
ContainsBlock(id)Can quickly reject a block absent from the chunk by scanning palette information.Maintain auxiliary summaries to avoid expensive full scans when justified.
FuzzyListBlockIds(...)Returns IDs present or potentially formerly present; false positives are allowed, false negatives are not.Approximate summaries can work as a fast filter if callers verify candidates where necessary.
ClearBlocksAndPrepare()Clears blocks and initializes the chunk-data palette for unsafe setting operations.Bulk generation may benefit from explicit preparation phases.
SetBlockUnsafe(...)Is not thread-safe and assumes the palette has already been initialized.Fast paths need clear preconditions and controlled ownership.
GetBlockId(index3d, layer)Reads a block ID at an index and specified layer.Cell data may have layers rather than one undifferentiated value.
GetFluid(index3d)Provides fluid access through the chunk-block interface.Investigate whether distinct cell layers or separate fluid storage best fit Hexel’s needs.

Limit: palette-related API behavior is documented, but the API docs alone do not prove the exact bit width of each stored index, the exact bit-packing layout, whether every chunk uses the same concrete representation, or memory usage for a particular terrain. Do not make quantitative memory claims until those details are verified or benchmarked.

Conceptual palette example

A palette stores the distinct materials used by a chunk; cell data stores an index into that palette. This is a conceptual illustration only and is not a reconstruction of Vintage Story’s internal encoding.

palette = [air, stone, soil, water]
cell palette indices = [0, 1, 1, 2, 0, 3]

If a chunk uses only a few distinct materials, palette indices may be cheaper than repeating full material IDs. If a chunk contains many distinct material states or palette updates are frequent, the benefits and update costs may differ. Measure both.

5. Separation of chunk responsibilities

The IWorldChunk API documents the following properties and behaviors:

MemberDocumented rolePossible relevance to Hexel
DataBlock IDs for each coordinate, accessed by linear index.Authoritative cell/material storage candidate.
LightingLighting data per coordinate, using the same documented index formula.Keep lighting separate from core occupancy/material data.
LightPositionsA HashSet<int> of in-chunk indices for light sources.Auxiliary set of relevant positions can avoid scanning all cells for some tasks.
BlockEntitiesA dictionary keyed by block position and containing block entities.Rich per-cell objects need not be embedded into every basic cell record.
Entities / EntitiesCountEntity array plus actual count.Dynamic entities can be tracked separately from terrain cells.
MapChunkReference to current map data for the chunk column.Separate 2D or regional summaries from 3D terrain.
MaybeBlocksFaster non-blocking reads that can sometimes return 0 instead of the actual block; intended for reading.Approximate/non-blocking query paths must be explicit and must not be used where correctness is required.
LiveModDataNon-serialized runtime data intended to avoid constant serialization/deserialization; populated by the caller from stored mod data as needed.Separate transient runtime caches from persisted state.
DisposedIndicates that a chunk was unloaded.Cached references need a clear lifetime/validity policy.
AcquireBlockReadLock()Allows bulk reads to pre-lock data layers; docs warn that heavy client-side use can delay rendering because the tesselator also needs read access.Concurrency optimizations must be measured and should avoid blocking the render path.

These documented distinctions suggest organizing data by purpose rather than putting everything in one cell object. They do not prove that Hexel should reproduce Vintage Story’s internal types or threading model.

Mutation, saving, and derived work are different concerns

The IBlockAccessor.SetBlock documentation describes updating a block and marking its chunk dirty for saving. It also describes layer-aware mutation for solid/liquid blocks and a neighbor-redraw method for cases where an operation affects ambient occlusion without using SetBlock. This is evidence that world mutation and neighbor rendering consequences need deliberate handling; it is not proof that save dirtiness and mesh dirtiness are the same flag.

For Hexel, track separately at the conceptual level:

  • Persistence dirtiness: authoritative data must be saved.
  • Mesh invalidation: geometry may no longer match authoritative cells.
  • Lighting invalidation: lighting may need recomputation.
  • Summary invalidation: surface or regional derived values may be stale.

Use change notifications to schedule only affected work, not to make every dependent system rebuild unconditionally.

6. 2D map-chunk data

The IMapChunk documentation explicitly describes an interface holding two-dimensional data for one chunk column. Documented properties include:

  • WorldGenTerrainHeightMap — terrain height at a world-generation stage, with the documentation explaining how ocean/lake seafloors are represented.
  • RainHeightMap — the position of the last block that is not rain-permeable before the first air block.
  • TopRockIdMap — rock block ID for the topmost rock layer.
  • SedimentaryThicknessMap — sedimentary thickness values.
  • SnowAccum — snow accumulation values.
  • YMax — highest position of any non-air block.
  • CurrentPass — current world-generation pass for the chunk column.

The interface also documents methods for persistent mod data and a MarkDirty() method that tells the server to save changes to the map chunk. Some map-chunk mod-data methods are documented as not implemented client-side and not synchronized from server to client; code should respect those documented limits.

Interpretation for Hexel

Surface and region summaries can speed up systems that need an overview of terrain. They are not substitutes for independent 3D occupancy: a highest-solid-height summary cannot describe caves, tunnels, arches, or floating terrain. Hexel should treat summaries as derived, invalidatable data and keep the full 3D cell representation authoritative.

7. JSON examples for Hexel

These examples define possible logical schemas for discussion. They are illustrative, not Vintage Story formats, and should not be interpreted as production serialization recommendations. JSON is readable but generally has too much overhead for millions of runtime cells; a compact binary representation is likely more appropriate after the logical model is settled.

Example A — palette-based chunk

{
  "chunk": {
    "coord": { "q": 2, "r": -1, "y": 0 },
    "dimensions": [16, 16, 16],
    "palette": ["air", "stone", "soil", "water"],
    "cell_encoding": "palette_indices",
    "cells_example": [0, 1, 1, 2, 0, 3],
    "version": 1
  }
}
  • coord identifies the chunk in axial-plus-vertical coordinates.
  • palette lists material types represented in this chunk.
  • cells_example shows palette indices, not material IDs; the array is abbreviated and does not contain all 4,096 cells.
  • air is included for clarity. A real implementation might use a special empty value or omit empty cells in sparse storage.

Example B — sparse occupied cells

{
  "chunk": {
    "coord": { "q": 2, "r": -1, "y": 0 },
    "storage": "sparse",
    "occupied_cells": [
      { "local": [0, 0, 0], "material": "stone" },
      { "local": [1, 0, 0], "material": "stone" },
      { "local": [1, 1, 0], "material": "soil" },
      { "local": [8, 4, 12], "material": "stone" }
    ]
  }
}

This resembles the general shape of a sparse representation: only occupied cells are listed. It is easy to inspect and may suit very sparse chunks, but JSON object/array overhead makes it unsuitable as a direct high-volume runtime format. Rust alternatives include a hash map, a packed coordinate key, or another sparse structure. The best choice depends on occupancy and access patterns.

Example C — authoritative data and derived state

{
  "chunk": {
    "coord": { "q": 2, "r": -1, "y": 0 },
    "terrain": {
      "storage": "sparse",
      "occupied_cells": [
        { "local": [0, 0, 0], "material": "stone" },
        { "local": [0, 1, 0], "material": "stone" }
      ]
    },
    "derived": {
      "mesh_dirty": true,
      "lighting_dirty": true,
      "surface_summary_dirty": true
    }
  }
}

The derived flags are hypothetical Hexel fields, not Vintage Story API fields. In a real engine these may belong in transient runtime state rather than persisted world data. The example emphasizes that a cell edit can invalidate several independent derived systems.

Example D — 2D region summary

{
  "region": {
    "coord": { "q": 2, "r": -1 },
    "surface_summary": {
      "highest_solid_y": 24,
      "surface_material": "grass",
      "average_moisture": 0.62
    },
    "summary_version": 3,
    "dirty": false
  }
}

These values are illustrative. A summary such as highest_solid_y is useful for selected queries but cannot encode the full 3D terrain. Its validity must be maintained when relevant cells change.

8. Architecture implications for Hexel Engine

Authoritative 3D hexel cells | | edits / generation / loading v Change tracking and targeted invalidation | | | | v v v v Mesh cache Lighting Region summaries Persistence

Suggested responsibilities:

  • Authoritative cells: answer whether a hexel exists at (q, r, y) and what material/state it contains.
  • Mesh cache: generate exposed faces from current cell state, including correct handling of chunk boundaries.
  • Lighting: store or derive lighting separately so that lighting changes do not force changes to the material representation.
  • Regional summaries: store useful derived facts such as surface height or biome inputs, with explicit invalidation rules.
  • Persistence: save authoritative changes; do not assume every runtime cache needs to be persisted.
  • Dynamic entities and block-attached data: avoid embedding rich runtime objects into every basic cell when a separate index or map will suffice.

Connection to reactive world architecture

These boundaries complement a dependency/invalidation system. Structural dependencies describe what can be affected; dynamic subscriptions express what a runtime system currently cares about; invalidation schedules recomputation when inputs change. They are related but distinct.

World state should remain authoritative. Events can inform dependent systems that something changed, while those systems query current state when recomputing. Batch and deduplicate invalidations to avoid repeated mesh rebuilds or synchronous callback cascades.

For a terrain edit, do not automatically recompute every region, mesh, or field. Identify the changed cell, affected neighbor faces, relevant chunk boundaries, and any dependent lighting or summary regions. Expand the work only when actual dependencies require it.

9. Storage trade-offs

ApproachLikely strengthsLikely costs / risksWhen to test it
Sparse map/set of occupied cellsEmpty cells need not consume a full per-cell slot; natural for very sparse terrain and incremental edits.Hashing and allocation overhead; neighbor traversal and full-chunk iteration can be less cache-friendly; coordinate storage costs.Baseline for caves, floating structures, and low-occupancy chunks.
Dense indexed chunkSimple address calculation, predictable iteration, potentially cache-friendly.Reserves logical slots for empty cells; cost scales with full chunk volume.Dense terrain and workloads with frequent local reads or meshing.
Palette-indexed chunkCan reduce material storage when a chunk uses relatively few distinct materials; palette summaries can support fast queries.Palette maintenance, encoding/decoding complexity, and material-state diversity may affect cost.Chunks dominated by a small set of common materials; compare edit and load costs as well as memory.
Hybrid/adaptiveMay suit different occupancy profiles by using different representations per chunk or section.More complex transitions, testing, and serialization; mixed representations complicate tooling.Only after simpler candidates have been measured and a clear performance win is demonstrated.

These are general data-structure expectations, not benchmark results for either Vintage Story or Hexel. Measure rather than infer performance from the API shape alone.

10. Recommended experiments

  1. Keep a baseline. Record current sparse storage behavior and representative test worlds before changing implementation.
  2. Define representative workloads. Include solid terrain, mostly empty chunks, cave systems, tunnels, overhangs, floating structures, and high material diversity.
  3. Benchmark three candidates. Compare sparse occupied cells, dense indexed storage, and palette-indexed storage with the same world and workload.
  4. Measure distinct costs. Record memory per loaded chunk, cell lookup, insertion/removal, neighbor queries, exposed-face meshing, mesh rebuild latency, and save/load time.
  5. Test correctness independently. Verify coordinate-to-index round trips, negative axial coordinates, chunk-boundary edits, empty cells, caves/overhangs, and invalidation of adjacent chunks.
  6. Keep caches separate. Track persistence dirtiness, mesh invalidation, lighting invalidation, and summary invalidation as distinct concerns.
  7. Choose based on evidence. Do not adopt palette encoding or adaptive storage until it offers a measurable improvement that justifies its implementation complexity.
